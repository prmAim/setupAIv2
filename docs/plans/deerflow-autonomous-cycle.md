# План реализации автономного цикла на DeerFlow

Статус: согласован владельцем 27.11.2026; этап 2 подтверждён офлайн, полный цикл ещё не принят.

Актуальное уточнение 27.11.2026: владелец выбрал встроенный CodexChatModel и
поручил подготовить интеграцию, refresh авторизации и отмену **без живого запуска**.
Подготовлен отдельный candidate profile, backport upstream cancellation и
managed refresh через официальный Codex; [эксплуатация](../../infra/deerflow/CODEX.md).
Собственный SIWC canary больше не является обязательным предшественником
этого пути. Исторические указания отправить Support/повторить canary
не являются разрешением на новую попытку. Этап 2 требует отдельной live-приёмки;
полный цикл и действующая политика merge сохраняются.

Основание: [главная цель](../../CONTEXT.md) и
[выбранная платформа DeerFlow, ADR-0001](../adr/0001-deerflow-runtime.md).

**Issue → план → изменение кода → проверки → исправление или остановка → доказательства → PR → проверка PR → слияние в `main` → следующая Issue.**

Агент выполняет цикл самостоятельно, включая ночью, соблюдая согласованные
условия проверок и слияния. Первый проект — Orbita, затем Fortune.

## Этап 1. Схема интеграции

Для каждого шага цикла определить механизм DeerFlow, пригодные компоненты
setupAIv2, недостающую интеграцию и проверяемый результат. Проверить текущие
версии и фактический код, затем связать работы с существующими Issues.

Исследовать повторное использование выбора и закрепления Issue (#28–29),
публикации (#30 / PR #35), проверок области diff и целостности тестов,
контейнерного runner, восстановления и сбора доказательств.
Разработка распределена между ветками и worktree; текущая ветка не содержит
все результаты. Начать с `git worktree list` и чтения соответствующих источников.

Результат: короткая схема ответственности и последовательность конкретных
работ. Явно отделить уже подтверждённое поведение от требующей проверки интеграции.

## Этап 2. Модель и сохранение состояния

Встроенный `CodexChatModel` DeerFlow v2.2.0 исследован; подготовлены отдельный
профиль, async backport и управление авторизацией. Офлайн-доказательства —
[отчёт интеграции](../validation/deerflow-codex-integration-20261127.md).
Совместимость с настоящим аккаунтом ещё требует живой приёмки. Предпочтение владельца — существующая подписка
Codex; автоматический переход на платный API не предусмотрен.

Провести ограниченную проверку подключения по применимым разрешениям, затем
прервать небольшую задачу и возобновить её. Проверить сохранение Issue, цели,
решений, плана, выполненных шагов, проверок и следующего действия.
Долговременная память, история чата и контрольная точка исполнения имеют разные
роли; приёмка должна подтверждать восстановление работы без повторных эффектов.

Результат: подтверждённый путь вызова модели и воспроизводимый отчёт
прерывания/возобновления либо точная причина блокировки.

## Этап 3. Одна Issue Orbita через полный цикл

Подключить инструменты GitHub, рабочую область и отдельный изолированный runner.
В текущем профиле DeerFlow доступны только файловые инструменты; выполнение
тестов требует отдельной исполнительной среды без секретов Gateway.

На небольшой подходящей Issue выполнить полный цикл под наблюдением:
план, правки, проверки, ограниченные исправления, доказательства, PR,
независимое ревью и обязательные CI-проверки актуального head SHA, слияние
по согласованной политике. Зафиксировать разрешения на пилот и условия слияния
из действующих решений до внешних действий. Этот план не обходит условия допуска.

Результат: ссылки на Issue и PR, SHA, результаты проверок и ревью,
трасса этапов, подтверждение слияния. Успешная публикация PR — промежуточный этап.

## Этап 4. Очередь и восстановление

Проверить две задачи подряд без ручной передачи между ними, пустую очередь,
красные проверки, исчерпание лимита и перезапуск. Подтвердить корректный переход
к следующей доступной Issue либо сохранённую причину остановки, отсутствие
повторных claim, PR и других подтверждённых внешних действий.

Результат: отчёт по каждому сценарию с наблюдаемым состоянием до и после.

## Этап 5. Ночной запуск и Fortune

После предыдущих этапов провести ночной запуск на ограниченной очереди
со согласованными лимитами и политикой слияния. Подключить Fortune отдельным
профилем и проверить тот же цикл с разделением памяти, доступов и рабочих областей.

Результат: отчёт ночного выполнения и подтверждение работы второго профиля.

## Актуальная точка продолжения — 27.11.2026

- Этап 1 описан в [историческом отчёте](../validation/deerflow-autonomous-cycle-20261127.md).
- Этап 2 подтверждён офлайн: native CodexChatModel, refresh/cancellation,
  synthetic embedded checkpoint/resume. [PR #36](https://github.com/prmAim/setupAIv2/pull/36)
  слит в `main` (`f9cca1d`), обе CI-проверки прошли на `b2d0674`.
- #28/#29 присутствуют в main; при согласовании ветки сохранить их код,
  fixtures, тесты и общий CI. Windows пропускает Linux-only claim writer;
  это не заменяет Linux-проверку.
- Следующая работа: trusted execution handoff с проверкой claim, политика
  остановки и `cycle.stop_reason`, изолированный runner и интеграция PR.
  Эти части можно готовить офлайн. Публикация PR — промежуточный этап;
  независимое review/CI, merge по политике и следующая Issue остаются целью.
- Настоящая авторизация в выделенных volumes, model/tool probe, refresh,
  Gateway restart и production cutover требуют отдельного разрешения владельца.
  Сейчас действует запрет живого запуска; рабочие сервисы и данные сохраняются.
- SIWC canary/Support не являются обязательной зависимостью native-пути.
  Прежняя попытка использована; её не повторять, MIME/TLS не ослаблять.
- Langfuse восстановлен, вопрос миграции закрыт. Tracing candidate требует
  отдельной настройки и приёмки; merge PR не включает его автоматически.

При продолжении проверить текущий Git SHA, состав рабочей копии и состояние
Issues/PR: #30/PR #35, #31/#32 не считаются принятыми по одному факту merge #36.
Сохранять решения, проверки, границы и следующий шаг в отчёте этапа.
